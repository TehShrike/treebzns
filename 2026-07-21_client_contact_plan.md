# client_contact restructure plan (2026-07-21)

Reshape the existing `client_contact` table (it already exists — migration 0000, plus
`arbostar_contact_id` from 0016) so the ArboStar contact data imports as structured columns
instead of a merged display string, and capture the email-deliverability metadata the import
currently drops.

Target shape: `description` (from ArboStar's `cc_title`), `name`, `phone`, `email`,
`arbostar_email_data` (JSON snapshot of the `cc_email_*` / `email_unsubscribe` fields).

## Decisions already made (with Josh, 2026-07-21)

- **Rename in place**: `contact_name` → `name`. Imported rows keep the old merged
  `"Contact #1 John Smith"` string in `name` until the next re-import splits it (contacts are
  correlated by `arbostar_contact_id` and bulk-updated unconditionally). In-app rows (null
  `arbostar_contact_id`) are untouched — acceptable, none are expected to exist yet (no app
  code reads or writes `client_contact` at all; the only writer is the import).
- **Native JSON column**, named `arbostar_email_data` (not `email_notes`) — it is
  import-owned ArboStar data, like `arbostar_contact_id`. This is the schema's first JSON
  column, so the type-generation and mysql read paths need one-time plumbing (below).
- **Full snapshot for every imported contact** — not just contacts with notable flags.
  In-app contacts get NULL.
- **Filter boilerplate titles**: `cc_title` values matching `Contact #N` / `Contact N` /
  `Primary Contact` (case/whitespace-insensitive) import as `description = ''`. Only
  meaningful labels ("Property Manager", "Husband", "President", …) survive.

## Data profile (July 2026 export, 1,463 clients / 1,525 contacts)

Facts the implementation can rely on (verified against `arbostar_export/clients.js`):

- Every client has ≥ 1 contact; 60 have more than one; max 3.
- `cc_name` is never empty/blank; max length 34. `cc_title` max 34, `cc_email` max 46,
  `cc_phone_view` max 15 — everything fits the existing column widths.
- The client-row-level `cc_name`/`cc_phone`/`cc_email` exactly equal `contacts[0]`'s for all
  1,463 clients — including the 4 clients whose contacts array is not in `cc_id` order. So
  array order is ArboStar's own display order and first-is-primary is well-founded, not just
  a guess.
- Title distribution: 'Contact #1' ×1395, blank ×40, 'Contact #2' ×39, 'Contact 1' ×16,
  'Primary Contact' ×7, 'Contact #3' ×4, plus trailing-space variants ('Contact 1 ',
  'Property Manager '). ~20 contacts carry a real label.
- Email flags: `cc_email_check = 1` ×1344 (null ×67, rest 0), `cc_email_manual_approve = 1`
  ×135, `cc_email_blocked` ×18 (BOUNCE ×14, COMPLAINT ×4, each with a `YYYY-MM-DD`
  `cc_email_blocked_date`), `cc_email_unsubscribed` ×29, `email_unsubscribe` object non-null
  ×32 (shape: `{email, documentation, informational, reason}`).

## 1. Migration `migration/0026-client-contact-name-description-arbostar-email-data.sql`

```sql
ALTER TABLE client_contact
	RENAME COLUMN contact_name TO name,
	ADD COLUMN description VARCHAR(200) NOT NULL DEFAULT '' AFTER client_id,
	ADD COLUMN arbostar_email_data JSON AFTER email;
```

Resulting column order: …, client_id, description, name, phone, email, arbostar_email_data,
is_primary, … (matches the requested description/name/phone/email/email-data order).

Apply locally with the mysql cli using the `.env` credentials (per CLAUDE.md), then
regenerate schema types with `pnpm run local:db_export_schema`.

## 2. One-time JSON plumbing (first JSON column in the schema)

The convention chosen: **JSON columns are `string` in TypeScript** — the raw JSON text.
MySQL validates on write (a string literal inserted into a JSON column is cast and rejected
if invalid); readers `JSON.parse` when they care. This avoids inventing an `unknown`-typed
validator story for one archival column.

1. `scripts/export_schema.ts` — add to `MYSQL_TYPE_TO_TS`:
   ```ts
   json: () => 'string',
   ```
   (Without this the script asserts on the unknown data type and dies.)
2. `worker/lib/mysql/connection.ts` — add a branch to `typeCast` so JSON comes back as the
   raw text rather than mysql2's default (which JSON.parses into an untyped object):
   ```ts
   } else if (field.type === `JSON`) {
   	return field.string()
   ```
   (Nullable: `field.string()` already returns `string | null`.)
3. Write path needs nothing: `escape_value` escapes the JS string, MySQL casts it into the
   JSON column. Note MySQL normalizes stored JSON (key order/whitespace), so what comes back
   is not byte-identical to what was written — irrelevant here because the import's
   `bulk_update` writes unconditionally and never diffs stored values.

## 4. Import changes — `shared/arbostar/import_clients.ts`

Only `contact_fields` (line ~179) changes; correlation, insert/update flow, `is_primary`
(first contact), and `sort_order` (array index) all stay as they are. Both the
`bulk_update` and `bulk_insert` paths pick the new fields up automatically since they share
`contact_fields` — which is exactly how the next re-import repairs the renamed merged
`name` values on existing rows.

```ts
const BOILERPLATE_TITLE = /^\s*(contact\s*#?\s*\d+|primary\s+contact)\s*$/i

const contact_description = (title: string): string => {
	const trimmed = title.trim()
	return BOILERPLATE_TITLE.test(trimmed) ? '' : trimmed
}

const contact_email_data = (contact: ArbostarContact): string => JSON.stringify({
	email_check: contact.cc_email_check,
	email_manual_approve: contact.cc_email_manual_approve,
	email_blocked: contact.cc_email_blocked,
	email_blocked_reason: contact.cc_email_blocked_reason,
	email_blocked_date: contact.cc_email_blocked_date,
	email_unsubscribed: contact.cc_email_unsubscribed,
	email_unsubscribe: contact.email_unsubscribe,
})

const contact_fields = ({ contact, is_primary, sort_order }: (typeof incoming_contacts)[number]) => ({
	description: contact_description(contact.cc_title),
	name: contact.cc_name.trim() || `ArboStar contact ${contact.cc_id}`,
	phone: contact_phone(contact),
	email: contact.cc_email,
	arbostar_email_data: contact_email_data(contact),
	is_primary,
	sort_order,
})
```

Notes:
- The `ArboStar contact {cc_id}` fallback is kept (name is NOT NULL) even though `cc_name`
  is never blank in the July 2026 export.
- Snapshot keys are the export's fields with the `cc_` prefix dropped; values stored raw,
  no coercion. Written for **every** imported contact (full-snapshot decision).
- Still deliberately dropped from contacts: `cc_print` (a print flag, not email data),
  `cc_phone_ngrams` / `cc_phone_int` / `cc_phone_clean` (derivatives of `cc_phone`),
  timestamps.
- `join_lines` is no longer used for contacts but is still used for client notes — keep the
  import.
