Design notes

  • This page does not load 98.css. The office app can look like Windows 98. A page a customer reads before they spend four thousand dollars should not. It uses the same variables from global_variables.css, so the company brand color still drives it.
  • One price, one button. The design doc rules out tiered calls to action for now, so the total sits in one block with the approve button under it. Each line item shows its own price in small muted text (project_line_item.price), so the customer can see what each piece costs without the page reading like a bill.
  • Optional line items are checked by default, and the total drops when the customer unchecks one. A checkbox reads as "keep this", which is a smaller decision than "add this".
  • Only photos with visible_to_client show here. The estimator sets that flag when the photos come in.
  • Approving writes a project_client_approval row and moves the project to the next document. Both the office screen and this page use the same move.
  • Decline is a real button next to Approve, in the plain secondary style, with friendly help text under the pair. A declined answer beats a closed tab: it moves the project to the declined document and collects a project_decline_reason, instead of leaving the proposal to age out.
  • Open: does approval need a typed name or a drawn signature? project_client_approval.customer_signature is a blob and verbal_approval is a flag, so the schema holds either. src/notes/todo.md says close rates can not get worse, so the fewest taps wins.
  • Open: down payment. src/notes/big_todos.md wants 10% at approval. That adds a payment step between the button and the confirmation.
  • Open: what does the page show right after approval? It could switch straight to the work order view, which is the next page.
  • Open: expiration text. It says "this price holds until", but the schema note calls expiration "hide from reports after this many days". These are different promises.
