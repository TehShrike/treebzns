Design notes

  • The document path shows history, not the plan. It lists each project_document_history row in order, and marks the last one as current. The step names come from project_document.name.
  • One button moves the project to next_project_document_id. The button text names the target document, so the person reads an action, not a status.
  • The dropdown next to it holds the off-path documents: the declined document for the current one (declined_project_document_id), the other work order types, and Void. It needs the CAN_SET_ANY_DOCUMENT_STATUS permission.
  • The line item list under the Document section is a table of contents. Picking an item jumps to its photo-centric detail view. For now the list sits under the Document section. On wide screens it should later move to the left of the page, which needs responsive work.
  • Tax and discount inputs live in their own panel. A discount is one flat amount (discount) or one percent (discount_rate), never both, and it carries a discount_description. Line items have the same three columns, edited on the estimating screen.
  • The address and contact block reads from the project, not the client. The client link is there for people who need the full record.
  • Photos live at the project level. Each photo has one "customer can see" checkbox and a dropdown that links it to a line item.
  • Open: a photo can join to more than one line item in the schema (project_line_item_image), but the dropdown allows only one. Do we need many?
  • Open: the Money panel adds payments and balance, which the design doc does not ask for. Keep it here, or keep money on the client screen only?
  • Open: expiration. project_document.can_expire and expire_days exist, but the note in the design doc says the behavior should be "hide from reports after this many days". The Dates panel needs to say which one it is.
  • Open: hours worked need time_entry rows tied to a visit. time_entry.project_id points at the project, not at project_crew. src/notes/todo.md already lists this.
